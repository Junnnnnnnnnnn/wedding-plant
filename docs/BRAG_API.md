# 자랑하기 API 계약

프론트(`app/brag/*`, `app/components/BragToggle.tsx`)와 백엔드
(`~/DEV/seoul-moment-api` 의 `apps/api/src/module/plen/brag/`)가 **둘 다
이 계약대로 구현돼 있습니다.** 백엔드 확인은 그쪽 레포의
`test/plan.brag.spec.ts` 입니다.

응답은 앱의 다른 API 와 같은 `{ result: boolean, data: ... }` 입니다.
**금액 단위는 전부 만원**입니다 (`/plan/user/total-amount` 와 같음).

타입은 `types/index.ts` 의 `BragPost` · `BragDetail` · `BragPlanItem` ·
`BragMyStatus` 에 주석과 함께 있습니다.

---

## 이 기능이 무엇인가

대시보드에서 토글을 켜면 **내 플랜 한 장**이 자랑하기 목록에 올라갑니다.

- 올린 것은 **스냅샷이 아니라 라이브입니다.** 켜 두는 동안 지금 플랜이
  그대로 보입니다 — 일정을 더하거나 장소를 붙이면 자랑하기도 같이 바뀝니다.
  `plan_brag` 행에는 **"올렸다" 는 사실만** 있고(누가·언제부터·좋아요),
  예산·개수·카테고리·플랜 목록은 볼 때마다 새로 만듭니다.
- 다른 사람은 **보기와 좋아요**만 합니다. 댓글은 없습니다.
- **닉네임이 공개됩니다.**

### 피드와 규칙이 정반대라는 것을 잊지 마세요

피드(견적 후기)는 응답에 `planUserId` 조차 넣지 않는 **철저한 익명**입니다.
자랑하기는 반대로 **이름을 내는 것이 목적**입니다. 두 모듈의 코드를 서로
베낄 때 이 차이가 가장 먼저 사고가 납니다 — 피드 쪽에 닉네임을 흘리거나,
자랑하기 쪽에 익명 처리를 넣거나.

### 공개 범위 (안내 모달이 글자 그대로 약속하는 것)

> 닉네임 · 결혼식 날짜 · 총예산 · 카테고리별 지출과 소계 · 일정 제목 ·
> 일정별 금액 · 일정 장소

**이 목록에 없는 것은 응답에 넣지 마세요.** 특히:

- 일정의 **시각(`startTime`)** 과 **메모(`memo`)** — `BragPlanItem` 에
  일부러 없습니다.
- 채팅, 참여 멤버 목록, 프로필 이미지.

**장소(`location`·`lat`·`lng`)는 담습니다.** 상세 시트가 카카오 지도를
보여 주기 때문입니다. 카카오에서 고르면 `location` 에 업체명이 그대로
들어가므로 사실상 "어디서 했는지" 를 공개하는 것이고, 그래서 **안내 모달
문구를 먼저 고치고** 담았습니다. `lat`·`lng` 는 `decimal` 이라 드라이버가
문자열로 주므로 **반드시 `Number` 로 바꿔** 내보내세요 — 그대로 두면 앱이
`new kakao.maps.LatLng("37.5")` 를 불러 지도가 안 뜹니다.

장소를 담기 전에 올라간 스냅샷에는 이 값이 없습니다. 소급되지 않으므로 앱은
좌표가 없으면 지도를 아예 안 냅니다 — 내렸다 다시 올리면 그때 담깁니다.

- `planUserId` · `roomId` 같은 내부 식별자.

목록을 넓혀야 하면 **먼저 안내 모달 문구(`OPEN_FIELDS`)를 고치고** 응답을
고칩니다. 순서를 뒤집으면 동의받지 않은 것을 공개하게 됩니다.

## 엔드포인트

### `GET /plan/brag/list`

| 쿼리    | 기본값   | 설명                                 |
| ------- | -------- | ------------------------------------ |
| `page`  | `1`      | 1부터                                |
| `count` | `20`     | 한 번에 받을 개수                    |
| `sort`  | `RECENT` | `RECENT`(최신순) · `LIKED`(좋아요순) |

```
{ result: true, data: { list: BragPost[], total: number } }
```

`total` 은 전체 개수입니다 (더 받을 게 남았는지 프론트가 이걸로 판단합니다).

**`liked` 는 요청한 사람 기준**입니다. 목록에서 좋아요를 바로 누를 수 있어야
해서 카드마다 들어갑니다.

**`isMine` 이 있는 카드는 내려두기 버튼이 붙습니다.** 목록에서 자기 것을
바로 내릴 수 있어야 합니다 — 대시보드까지 돌아가게 하면 내리는 길이 멀어지고,
"언제든 내릴 수 있다"는 안내 모달의 약속이 흐려집니다.

### `GET /plan/brag/{bragId}`

```
{ result: true, data: BragDetail }
```

`BragDetail` = `BragPost` + `categoryChart` + `items`.
**모두 볼 때마다 그 사람의 지금 플랜에서 만듭니다.**

일정의 범위는 홈·보드가 쓰는 `getList` 와 **같아야 합니다** — 내가 만든
일정 가운데 방이 없거나 **내가 방장인 방**의 것. 남의 방에 조언자로 들어가
만든 일정은 내 플랜이 아닙니다.

- `categoryChart` — 예산 막대와 범례용. **지출 큰 순**으로 정렬해서 주세요.
  홈 대시보드의 `/plan/user/amount/category-chart` 와 같은 모양이고,
  **지출이 0 인 카테고리는 뺍니다**(막대에 낼 것이 없습니다).
  **개수는 서버가 자르지 않고 전부 줍니다.** 색은 `STACK_COLORS` 4개뿐이라
  앱이 상위 4개만 색을 주고 나머지는 **"그 외" 한 줄**로 합칩니다 — 서버가
  잘라 버리면 막대가 실제 지출보다 짧아집니다.
- `items` — 플랜 **전체**를 평평한 목록으로. 카테고리로 묶고 소계를 내는
  일은 프론트가 합니다. 소계는 **지출과 예정을 함께** 세야 하는데
  (완료 185 + 예정 35 = 220), 그 규칙을 서버에 두면 문구 하나 고치는 데
  백엔드 배포가 묶입니다.
- `status` 는 `"COMPLETED"` 면 완료, 그 밖은 예정으로 그립니다
  (`PlanTaskCard` 와 같은 규칙).

내 것이 아니어도 **누구나 조회할 수 있습니다.** 대신 내려간
(`published = false`) 플랜은 404 입니다 — 링크를 알아도 못 봅니다.

### `GET /plan/brag/my`

```
{ result: true, data: BragMyStatus }
```

대시보드 토글의 상태입니다. 한 번도 올린 적이 없으면
`{ published: false, bragId: null, publishedAt: null, likeCount: 0 }`.

### `PUT /plan/brag`

본문 없음. 지금 내 플랜의 **스냅샷을 떠서** 올립니다.

```
{ result: true, data: { bragId: number } }
```

- **스냅샷을 뜨지 않습니다.** 상태와 `publishedAt` 만 세웁니다.
- 이미 올라가 있으면 **아무것도 하지 않습니다**(멱등). `publishedAt` 도
  안 밀립니다 — 밀면 토글을 만질 때마다 목록 맨 위로 올라옵니다.
- 내려가 있던 것을 다시 올리면 **같은 행**을 쓰므로 좋아요가 이어집니다.
- 이름·결혼식 날짜·예산이 비어 있으면 거절합니다. 온보딩을 마치지 않은
  사람은 자랑할 내용이 없습니다.

### `DELETE /plan/brag`

내립니다. `{ result: true }`.

목록에서 사라지고 `GET /plan/brag/{id}` 는 404 가 됩니다.

**행을 지우지 않고 상태만 내립니다**(`status = UNPUBLISHED`). 다시 올릴 때
좋아요를 이어받으려면 그래야 합니다 — 지운 뒤에는 소급이 안 됩니다.

### `POST /plan/brag/like/{bragId}` · `DELETE /plan/brag/like/{bragId}`

```
{ result: true, data: { likeCount: number, liked: boolean } }
```

- 한 사람이 한 번. 같은 요청을 두 번 보내도 수가 늘지 않습니다.
- **자기 것에는 좋아요를 못 누릅니다** (`isMine` 이면 프론트도 버튼을
  내지 않지만, 서버에서도 막으세요).
- 프론트는 **낙관적으로** 그립니다 — 누르는 즉시 숫자를 바꾸고, 응답이
  오면 서버 값으로 맞추고, 실패하면 되돌립니다. 그래서 응답에 **최종
  `likeCount` 를 반드시** 실어 주세요.

## 방 권한과 무관합니다

피드와 같습니다. 자랑하기는 **방이 아니라 개인 자격**으로 올립니다 —
`READ`/`SPOUSE` 게이트를 넣지 마세요. 다만 올라가는 내용은 그 사람이 보고
있는 플랜(자기 플랜)이고, 남의 방을 자랑할 수는 없습니다.

## 정렬

- `RECENT` — `publishedAt DESC`
- `LIKED` — `like_count DESC, published_at DESC`

피드처럼 점수 컬럼을 따로 두지 마세요. 카운터가 둘이 되면 어긋날 자리가
하나 더 늡니다. `plan_brag.like_count` 를 `plan_brag_like` 행과 함께
`@Transactional()` 로 씁니다.

## 정해진 것

- **내렸다 다시 올리면 좋아요를 이어받습니다.** 행을 지우지 않고 상태만
  내립니다. 한 사람이 브래그를 **한 장만** 갖습니다(`plan_user_id` 유니크) —
  플랜 전체가 단위라 여러 장이 있을 이유가 없고, 토글이라 "지금 올라가
  있나" 가 상태의 전부입니다.
- **D-day 는 저장하지 않고 읽을 때 다시 셉니다.** 스냅샷이라고 D-24 를 박아
  두면 반년 뒤에도 D-24 라고 적힙니다. 저장하는 것은 결혼식 날짜뿐입니다.

## 아직 안 정해진 것

- **신고 버튼.** 닉네임이 공개되므로 피드보다 필요가 큽니다.
- 카테고리가 많은 플랜에서 상세 모달의 **묶음을 접을지.** 지금은 다 펴
  놓습니다.

## 확인

- 프론트: `node scripts/brag.cjs` — 백엔드를 목으로 세워 목록·상세·토글·
  안내 모달·좋아요(낙관적 갱신과 실패 되돌리기)를 실제로 눌러 봅니다.
  `npm run dev` 만 있으면 됩니다.
- 백엔드: 그쪽 레포에서 `docker compose -f docker-compose.test.yml up -d`
  뒤 `npm run test:integration -- --testPathPattern plan.brag` (17개).
  스냅샷 값, 공개 범위, 좋아요 이어받기, 자기 것 좋아요 금지를 봅니다.
