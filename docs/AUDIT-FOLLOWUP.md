### C. 백엔드

- `/plan/schedule/list?roomId=` 가 roomId 필터를 지원하지 않는 것으로 보임
  (방 플랜 조회는 `/plan/schedule/room/{code}/list` 사용). 확인 필요.
- `PATCH /plan/user` 가 `requiredAgreementDate` · `adAgreementDate` 를 둘 다 문자열
  필수로 요구한다. 마케팅 미동의를 표현할 방법이 없어 프로필 저장은
  `POST /plan/setting` 으로 우회해 둔 상태다. 선택 항목으로 바꾸는 것이 근본 해결.
- `GET /plan/room/:roomId` 에 멤버십 검사가 없다. 로그인한 사용자면 아무 방이나
  멤버 목록을 조회할 수 있다.
- `dev` 브랜치에 `main` 의 수정(캘린더 status, 스케줄 권한 검사)이 반영돼 있지 않다.
  당분간 `dev` 를 쓰지 않기로 했지만, 재개할 때 반드시 먼저 머지할 것.

## 보고서에서 정정된 것

실행 검증 결과 보고서 내용이 틀렸거나 조건이 달랐던 항목들. 다시 볼 때 혼동하지 않도록 남긴다.

| 항목                          | 정정 내용                                                                                                                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| W10                           | **재현되지 않음.** 채팅방을 읽으면 탭·방 배지가 정상적으로 사라지고 서버 카운트도 6→0. "다른 방 카운트 유실"은 채팅이 **1:1 구조**라 방이 하나뿐이므로 발생할 수 없다.               |
| W12                           | **틀림.** `ChatRoomCreateModal` 에는 실패 처리(else 분기)가 있었다. 실제 문제는 백엔드 raw 메시지를 그대로 노출한 것이었고, 채팅방 추가 UI 자체를 제거하면서 해소됐다.               |
| W17                           | 1:1 구조라 방 전환 시나리오가 존재하지 않는다. **해당 없음.**                                                                                                                        |
| W40                           | 인접 월이 비는 것은 **로그인 상태에서만** 발생했다. 게스트 모드는 로컬 그룹핑이라 정상이었다.                                                                                        |
| W41                           | 완료 표시는 **게스트 모드에서도** 안 됐다. 원인이 백엔드만이 아니라 클라이언트에도 있었다(`status: undefined` 하드코딩).                                                             |
| W48                           | **재현되지 않음.** 완료 탭에서 정렬을 바꿔도 목록이 유지됐고 추가 조회도 없었다.                                                                                                     |
| W30                           | 로그인 계정으로는 재현 못 함. 백엔드가 예산 0을 받지 않는다. `\|\| 1000` 폴백은 게스트 모드에서만 유효.                                                                              |
| `/plan/user` 의 roomId 비대칭 | **버그가 아니다.** 참여자도 자기 플랜을 따로 갖는 구조이고, `roomId` 는 "내가 소유한 방"을 뜻한다. 참여자의 roomId를 남의 방으로 채우면 그 사람 자신의 플랜이 `/main` 에서 사라진다. |

## 이어서 하려면 (환경 재구성)

두 계정이 필요한 검증(권한·협업·채팅)은 아래 환경으로 했다.

```bash
# dev 서버
npm run dev

# 계정 A 창 (디버깅 포트 9222)
"C:/Program Files/Google/Chrome/Application/chrome.exe" \
  --remote-debugging-port=9222 \
  --user-data-dir="C:/Users/zipshow_backend/chrome-debug-profile" \
  http://localhost:3000

# 계정 B 창 (디버깅 포트 9223)
"C:/Program Files/Google/Chrome/Application/chrome.exe" \
  --remote-debugging-port=9223 \
  --user-data-dir="C:/Users/zipshow_backend/chrome-debug-profile-2" \
  http://localhost:3000
```

- 로그인은 각 창에서 **직접** 한다. 프로필이 남아 있으면 재로그인 없이 복원된다.
- puppeteer-core 로 `browserURL: http://localhost:9222` 에 붙어 조작한다
  (`npm install --no-save puppeteer-core`).
- 창이 가려져 있으면 `document.visibilityState === "hidden"` 이 되어 일부 동작이
  느려질 수 있다. 필요하면 `page.bringToFront()`.

### 현재 테스트 계정 상태

- A(야호): 방 소유자, `roomId=1`, 채팅방 1개
- B(게스트테스터): A의 방에 WRITE 로 참여. 자기 플랜도 별도 보유
- 방을 나가는 엔드포인트가 없어 참여 상태는 그대로 남아 있다
- 채팅방 1번에 테스트 메시지 몇 건이 남아 있다 (정리하려면 직접 삭제 필요)
