### 검증 방식 메모

권고 항목은 대부분 눈으로 확인하기 어려워, **수정 전 코드로 되돌려 같은
시나리오를 다시 돌리는 대조 방식**으로 확인했다. 다시 손볼 때 참고:

- 로그인 세션이 필요한 화면은 백엔드 응답을 puppeteer 요청 인터셉트로 목
  처리했다. 이때 `Access-Control-Allow-Origin` 등 CORS 헤더를 함께 주고
  `OPTIONS` 프리플라이트에도 응답해야 한다. 안 그러면 전부 CORS 로 막힌다.
- 화면에 붙어야만 보이는 컴포넌트(토스트·가이드·지출 분석)는 `app/` 아래에
  임시 프리뷰 라우트를 만들어 캡처하고 지웠다. `_` 로 시작하는 폴더는
  Next 가 private folder 로 무시하므로 이름에 쓰지 말 것.

### W43 READ 분기 — 확인 완료, 그리고 더 중요한 발견

`scripts/room-permission-ui.cjs` 로 확인했다. WRITE 는 "+"와 "플랜
추가하기"가 보이고 READ 는 둘 다 숨는다.

**다만 READ 권한은 현재 제품에서 도달할 수 없다.**

- 공유 코드로 참여하면 백엔드가 항상 `WRITE` 를 부여한다
  (`plan-room.service.ts` `postPlanRoom`)
- 권한을 바꾸는 엔드포인트가 백엔드에 없고(=`permission` 을 수정하는 코드
  0건), 프론트에도 권한 변경 UI 가 없다
- 엔티티 기본값만 `READ` 인데 참여 경로가 `WRITE` 를 명시로 넘겨 쓰이지 않는다

그래서 `/main` 의 기존 READ 게이트와 이번에 추가한 캘린더 게이트는 지금은
발생할 수 없는 상태를 방어하고 있다. 계정을 두 개 만들어도 READ 화면은 볼
수 없어, `/plan/room/{id}` 응답만 목으로 바꿔 프론트 분기를 태웠다.
(공유 백엔드라 DB 는 직접 건드리지 않았다)

**제품 판단이 필요한 부분:** 읽기 전용 참여자가 기획에 있는 기능이라면
백엔드에 권한 지정·변경 수단이 있어야 하고, 없는 기능이라면 프론트의 READ
분기들은 죽은 코드다. 어느 쪽인지 정해야 한다.

## 이어서 하려면 (환경 재구성)

두 계정이 필요한 검증(권한·협업·채팅)은 아래 환경으로 했다.

```bash
# dev 서버
npm run dev

# 계정 A 창 (디버깅 포트 9222)
"C:/Program Files/Google/Chrome/Application/chrome.exe" \
  --remote-debugging-port=9222 \
  --user-data-dir="C:/Users/zipshow_backend/chrome-debug-profile" \
  http://localhost:3000

# 계정 B 창 (디버깅 포트 9223)
"C:/Program Files/Google/Chrome/Application/chrome.exe" \
  --remote-debugging-port=9223 \
  --user-data-dir="C:/Users/zipshow_backend/chrome-debug-profile-2" \
  http://localhost:3000
```

- 로그인은 각 창에서 **직접** 한다. 프로필이 남아 있으면 재로그인 없이 복원된다.
- puppeteer-core 로 `browserURL: http://localhost:9222` 에 붙어 조작한다
  (`npm install --no-save puppeteer-core`).
- 창이 가려져 있으면 `document.visibilityState === "hidden"` 이 되어 일부 동작이
  느려질 수 있다. 필요하면 `page.bringToFront()`.

### 현재 테스트 계정 상태

- A(야호): 방 소유자, `roomId=1`, 채팅방 1개
- B(게스트테스터): A의 방에 WRITE 로 참여. 자기 플랜도 별도 보유
- 방을 나가는 엔드포인트가 없어 참여 상태는 그대로 남아 있다
- 채팅방 1번에 테스트 메시지 몇 건이 남아 있다 (정리하려면 직접 삭제 필요)
